# Achados técnicos para revisão com a equipe

Lista consolidada de achados transversais/notáveis encontrados durante o mapeamento completo de tabelas em [[Dominio]] (ver tabela de progresso por bloco lá). Cada achado também está documentado no arquivo da tabela específica — este arquivo existe só para facilitar uma revisão única com o time, sem precisar abrir os ~330 arquivos individuais. Organizado por bloco, na ordem em que foi encontrado.

Para cada item aqui, ver [[Plano-de-Acao]] — solução proposta, ponderações e esforço estimado, com uma versão interativa publicada em [Raio-X do Schema](https://claude.ai/code/artifact/ab2e8966-2656-459c-b64c-a167289943ac).

## Bloco 1 — Estoque & Produto

- **[[locais_estoque]]**: dois modelos idênticos em arquivos diferentes (`estoque_local_models.py` vs `local_estoque_models.py`); o único service que usa um deles (`estoque_transferencia_service.py`) tem import quebrado (`EstoqueLocal` não existe) e referencia campos (`sku`, `local_estoque_id`, `quantidade`) que não existem em nenhum dos dois modelos reais. As rotas que dependem desse service (`estoque_importacao_csv_routes.py`, `estoque_importacao_pdf_routes.py`) não estão registradas no app (não achei `include_router`). Tratar como dead code quebrado — recomendo confirmar com o time antes de decidir qual consolidar/remover.
- ✅ **CORRIGIDO (2026-09-14)** — **[[kit_composicao]]**: duplicação análoga, mas ambos os arquivos são "mortos" do ponto de vista de lógica de negócio — um nunca é importado, o outro só é registrado para o Alembic enxergar a tabela, sem nenhum service/rota lendo ou escrevendo nela. A lógica de kit realmente usada é [[produto_kit_componentes]]. *Removido o arquivo órfão `app/kit_composicao_models.py` (zero referências confirmadas); mantido `app/fiscal_models/kit_composicao.py`, que ainda alimenta o Alembic.*
- **[[listas_preco]]/[[produto_listas_preco]]**: modelo e relationships completos, mas sem nenhuma rota CRUD localizada — só leitura passiva em integração e-commerce e manipulação em merge de produtos. Possível feature incompleta.
- **Padrão `ondelete`**: maioria das FKs para `produtos.id` usa `CASCADE` ou nenhum `ondelete` explícito, mas o módulo de fracionamento clínico ([[estoque_fracionamento_vinculos]]) usa `RESTRICT` deliberadamente — provavelmente para impedir apagar produto com histórico clínico de fracionamento.
- **Inconsistência de serialização JSON**: [[estoque_movimentacoes]]`.lotes_consumidos` é `Text` com JSON manual, enquanto [[estoque_fracionamento_conversoes]]`.lotes_origem_consumidos`/`.lotes_destino_criados` usa coluna `JSON` nativa — mesma necessidade, implementações diferentes (a segunda é mais nova/correta).
- **[[produto_fornecedores]]`.fornecedor_id`** aponta para `clientes.id`, não para uma tabela de fornecedores dedicada — confirma que o cadastro de pessoas é unificado em [[Cliente]].

## Bloco 2 — Vendas & Caixa & Formas de Pagamento

- ✅ **CORRIGIDO (2026-09-14)** — **[[operadoras_cartao]]**: duplicação confirmada, mesmo padrão do Bloco 1 — `operadoras_cartao_models.py` define uma segunda classe `OperadoraCartao` para a mesma tabela, mas **nunca é importada em lugar nenhum** (app, Alembic, testes), e seu schema nem corresponde à tabela física real (a migração `zwr20260821a1_card_fee_rules.py` usa o schema de `operadoras_models.py`). Modelo em uso de verdade: `operadoras_models.py`. *Arquivo órfão `app/operadoras_cartao_models.py` removido.*
- **[[formas_pagamento_comissoes]]**: tabela órfã — e o próprio código-fonte já se autodocumenta como tal (comentário "FORMAS PAGAMENTO COMISSÕES (ÓRFÃ)" citando um relatório interno `RELATORIO_SCHEMA_TABELAS_ORFAS.md - Fase 5.4`). Nenhuma rota/service usa.
- **[[venda_baixas]]**: só é lida (`ecommerce_entregador.py`), nunca escrita via ORM em código de aplicação — os únicos INSERTs achados são em scripts de seed. Indício de que o fluxo real de baixa de venda a prazo migrou para [[ContaReceber]]/`VendaPagamento` e esta tabela pode estar obsoleta. Precisa confirmação do time.
- **Padrão recorrente de "FKs fantasmas"**: vários campos com nome de relação (`operadora_id`, `forma_pagamento_id`, `taxa_cartao_regra_id` em [[venda_pagamentos]]; `usuario_id`/`conta_origem_id` em [[caixas]]; `fornecedor_id`/`conta_origem_id`/`conta_destino_id`/`usuario_id` em [[movimentacoes_caixa]]) são `Integer` soltos, **sem `ForeignKey()` real** — dívida técnica de integração incompleta entre os módulos de vendas, caixa e operadoras de cartão. Comentários no próprio código (`# was: ForeignKey(...) - tabela não existe`) confirmam que isso é resquício de refactor, hoje desatualizado (a tabela existe, a FK nunca foi restaurada).
- **[[caixas]]**: valores monetários (`valor_abertura`, `valor_esperado`, etc.) usam `Float`, não `DECIMAL` — inconsistente com o padrão `DECIMAL(10,2)` do módulo de vendas; risco de arredondamento.

## Bloco 3 — Financeiro & DRE & Conciliação & Comissões

Este foi o bloco mais denso em achados até agora — 32 tabelas, vários padrões sistemáticos:

- **Comentário "tabela não existe" copiado entre 3 arquivos, todos errados**: [[conciliacao_logs]]`.conciliacao_validacao_id` e [[conciliacao_recebimentos]]`.validacao_id` são ambos `Integer` sem `ForeignKey()` real, com o comentário `"FK desabilitado - tabela conciliacao_validacoes não existe"` — mas [[conciliacao_validacoes]] **existe** desde sempre, no mesmo arquivo `conciliacao_models.py`. Parece um comentário copiado/colado entre módulos sem verificar a premissa. Recomenda-se restaurar as duas FKs.
- **`formas_pagamento.operadora_id`** ([[formas_pagamento]]): mesmo padrão — comentário diz que `operadoras_cartao` "não existe", mas existe (é o mesmo achado de dead code do Bloco 2, [[operadoras_cartao]]). FK nunca foi restaurada.
- **Duas tabelas de comissão com ORM não usado**: [[comissoes_configuracao]] e [[comissoes_vendas]] têm classe SQLAlchemy definida, mas nenhuma rota/service a usa — o acesso real de produção é via SQL cru numa classe paralela (`ComissoesConfig`, métodos estáticos em `comissoes_models.py`). Duas camadas de acesso concorrentes para a mesma tabela física.
- **[[provisoes_automaticas]]**: modelo descrito no código ("provisões automáticas para contas recorrentes") mas sem nenhum uso confirmado fora da própria definição — parece feature nunca implementada.
- **Armadilha de nomenclatura entre dois módulos de conciliação diferentes**: [[templates_adquirentes]] (`TemplateAdquirente`, conciliação bancária genérica) vs [[adquirentes_templates]] (`AdquirenteTemplate`, conciliação de cartões Fase 1) — nomes quase espelhados, tabelas e propósitos diferentes.
- ✅ **CORRIGIDO (2026-09-14)** — **Colisão de nomes de classe entre ORM e schema de API**: `ComissaoItem` existe como tabela real ([[comissoes_itens]], `comissoes_models.py`) E como schema Pydantic sem tabela (`comissoes_avancadas_models.py`) — mesma coisa com `FormaPagamento`. Grepar só pelo nome da classe sem checar o import leva ao arquivo errado. *Classes Pydantic renomeadas para `ComissaoItemSchema`/`FormaPagamentoSchema`, com docstring explicando a distinção; único call site externo (`conferencia_routes.py`) atualizado.*
- **[[conciliacao_lotes]]**: relationship pretendido com [[ContaReceber]] nunca implementado (comentado no código como "ContaReceber não tem back_populates") — o vínculo hoje é só um contador manual (`quantidade_parcelas`), sem FK ou tabela de associação garantindo integridade.
- **[[historico_classificacao_dre]]**: campo de valor monetário (`valor`) é `Integer` (centavos) em vez de `Numeric`, inconsistente com o padrão do resto do módulo financeiro.
- **[[duplicatas_ignoradas]]**: a `UniqueConstraint` do par de produtos não normaliza a ordem — `(5,3)` e `(3,5)` não colidem no banco, a garantia de "menor ID primeiro" (citada no docstring) é só convenção de aplicação, não constraint.

## Bloco 4 — Compras (pedidos de compra, notas de entrada)

- **Dupla fonte de verdade pedido↔nota**: [[pedidos_compra]]`.nota_entrada_id` (campo direto, usado só no fluxo de "confronto" NF×pedido) coexiste com a tabela de junção N:N [[pedidos_compra_notas_entrada]] (via "oficial", com `UniqueConstraint`). O código de negócio precisa checar os dois lugares (`_pedido_principal_da_nota`), priorizando o vínculo N:N e caindo pro campo direto como fallback. Recomenda-se avaliar deprecar o campo direto.
- **Dois caminhos paralelos de entrada física em estoque a partir de compras**: via recebimento de pedido ([[pedidos_compra_itens]], `pedidos_compra/recebimento_routes.py`, cria `ProdutoLote` direto) e via processamento de nota de entrada ([[notas_entrada]], `notas_entrada/processamento_routes.py`) — não ficou claro nesta pesquisa se os dois fluxos são mutuamente exclusivos na prática ou se podem colidir/duplicar entrada de estoque para o mesmo recebimento.
- **FK fantasma recorrente em `fornecedor_id`**: presente em [[pedidos_compra]], [[notas_entrada]] e [[compras_pendencias_fornecedor]] — sempre `Integer` sem `ForeignKey()`, resolvido em runtime contra [[Cliente]]. Mesmo padrão já visto no módulo financeiro.
- **[[notas_entrada]] é hub central confirmado**: gera [[ContaPagar]] (`notas_entrada/financeiro.py`), gera `ProdutoLote`+atualização de estoque, e gera [[produtos_historico_precos]] quando altera custo — vale conhecer essa tabela bem se for mexer em qualquer parte do fluxo de compras.
- **Desnormalização deliberada em [[compras_pendencias_fornecedor]]**: `fornecedor_nome`/`cnpj`/`numero_nota`/`numero_pedido` são snapshot em texto (correto para histórico de comunicação por e-mail), mas podem divergir do estado atual das tabelas de origem.
- Nenhuma duplicação de `__tablename__` (classe morta) encontrada neste bloco — diferente do padrão dos blocos 1-2.

## Bloco 5 — Fiscal (NF-e, Simples Nacional, config fiscal)

🔴 **Este bloco contém o achado mais sério do mapeamento até agora — recomenda-se priorizar esta seção na revisão com o time.**

- ✅ **CORRIGIDO (2026-09-14)** — **Duplicação com risco real de crash (não só dead code inofensivo)**: [[fiscal_catalogo_produtos]] e [[fiscal_estado_padrao]] têm duas classes ORM cada mapeando o mesmo `__tablename__`, usando o **mesmo objeto `Base`/registry** SQLAlchemy. Foi reproduzido isoladamente (script de teste fora do repo) que registrar as duas classes na mesma `MetaData` lança `sqlalchemy.exc.InvalidRequestError: Table already defined for this MetaData instance`. Hoje isso não derruba o servidor porque o runtime do FastAPI nunca importa o caminho da cópia órfã (`app.fiscal_models`/`app.db.base`, usado só por Alembic e 2 scripts de seed) — mas é uma bomba-relógio: qualquer refactor, teste de integração completo, ou script que una os dois grafos de import quebra o processo. *Cópias órfãs removidas; `fiscal_models/__init__.py` agora reexporta dos módulos canônicos top-level, mesmo padrão já usado para `KitConfigFiscal`/`ProdutoConfigFiscal`. Verificado por importação real: `app.db.base` (o módulo que o Alembic usa) carrega os 150 modelos sem lançar `InvalidRequestError`.*
- ✅ **CORRIGIDO (2026-09-14)** — **Dois routers inteiros de código morto, nunca registrados no app**: `nota_fiscal_rateio_routes.py` e `nota_fiscal_item_rateio_routes.py` (tabelas [[nota_fiscal_rateio_canal]] e [[nota_fiscal_item_rateio_canal]]) não aparecem em nenhum `include_router` — inalcançáveis via HTTP. O segundo é mais grave: contém SQL cru (com comentário literal `🔴 AQUI assumimos que você já tem...`) contra uma tabela `nota_fiscal_itens` que **não existe em nenhum model ou migration do projeto**, e usa `db.execute()` com string crua (inválido no SQLAlchemy 2.x do projeto) — rascunho nunca finalizado nem testado. *Os dois routers e seus helpers exclusivos (`nota_fiscal_rateio_helper.py`, `nf_item_rateio_validator.py`) foram removidos. As tabelas [[nota_fiscal_rateio_canal]]/[[nota_fiscal_item_rateio_canal]] em si NÃO foram tocadas (permanecem no banco) — se "rateio por canal" ainda for necessidade real, o desenho correto é reaproveitar [[bling_notas_fiscais_cache]].*
- **FK fantasma com comentário desatualizado, e efeito prático confirmado**: `empresa_config_fiscal.fiscal_estado_padrao_id` tem comentário "Temporariamente sem FK até fiscal_estado_padrao ser recriado" — mas a tabela existe e é usada ativamente. Pior: a única função que preenche essa coluna (`criar_config_fiscal_empresa`) nunca é chamada em produção; o caminho real (`obter_ou_criar_config_fiscal_empresa_padrao`) nunca seta o campo — na prática, `fiscal_estado_padrao_id` fica sempre `NULL`.
- **Desenho duplicado nunca plugado**: [[bling_notas_fiscais_cache]] (tabela real, ativamente usada) já guarda um único canal por NF; as duas tabelas mortas de rateio por canal ([[nota_fiscal_rateio_canal]]/[[nota_fiscal_item_rateio_canal]]) foram desenhadas para permitir múltiplos canais por percentual, mas nunca chegaram a ser conectadas ao fluxo vivo.
- **Achado positivo, útil como referência**: [[produto_config_fiscal]] já teve uma duplicação idêntica no passado (cópia em `fiscal_models/`) e o time **já a removeu corretamente** — prova de que o padrão de correção é conhecido e viável, só falta aplicar aos dois casos ainda pendentes acima.
- **`variacao_config_fiscal.variacao_id`**: aponta para uma tabela `produto_variacao` que não tem model ORM nem migration — mesmo padrão já visto em [[kit_composicao]] (variações hoje são modeladas como `Produto.tipo_produto='VARIACAO'`, não uma tabela própria).
- **Cadeia de resolução fiscal do PDV confirmada e útil para onboarding**: `KitConfigFiscal → VariacaoConfigFiscal → ProdutoConfigFiscal → EmpresaConfigFiscal` (`services/pdv_fiscal_resolver.py`), do mais específico para o mais genérico.

## Bloco 6 — Veterinário (~25 tabelas)

- **Procedimento veterinário não passa pelo módulo de Vendas**: [[vet_procedimentos_consulta]]`._sincronizar_financeiro_procedimento` cria [[ContaReceber]] diretamente por procedimento realizado (idempotente via `documento` único `VET-PROC-{id}-...`), sem nunca criar registro de [[Venda]]. Importante para quem for montar relatórios agregados de faturamento — filtrar só por `vendas` deixa de fora todo o faturamento veterinário.
- **[[vet_partner_link]] — compartilhamento de dados entre tenants**: quando um veterinário opera como "parceiro" de uma loja (tenants diferentes), o sistema gera automaticamente DUAS contas a receber por procedimento (receita líquida do vet + repasse da empresa), e `tenancy/filters.py` usa esse vínculo para permitir que o tenant da empresa "enxergue" dados do tenant do veterinário parceiro. É um caso deliberado e sensível de exceção à isolação multi-tenant — recomenda-se auditoria de segurança para confirmar que o filtro é sempre aplicado e não pode ser burlado.
- **Prescrição (receituário) desconectada do estoque**: [[vet_itens_prescricao]]/[[vet_medicamentos_catalogo]] são puramente informativos — nenhuma FK nem lógica de baixa liga medicamento prescrito a `produtos`/estoque. O catálogo de medicamentos veterinários e o catálogo de produtos comerciais são dois mundos paralelos.
- **Inconsistência de referência a produto entre tabelas irmãs**: [[vet_procedimentos_consulta]]`.insumos` guarda `produto_id` só dentro de JSON solto (sem FK), enquanto [[vet_orcamento_itens]]`.produto_id` é FK real — duas tabelas semanticamente parecidas (insumo de procedimento vs. item de orçamento) com padrões de referência diferentes.
- **[[vet_orcamentos]] "sem movimentar estoque" (por design)** — mas não foi encontrada rota que converta um orçamento aceito em procedimento/venda real automaticamente. Pode ser lacuna de fluxo ou conversão manual — vale confirmar com o time.
- **Padrão "veterinário = Cliente"**: não existe tabela própria de veterinário/funcionário clínico — `veterinario_id` é sempre FK para `clientes.id`, com a convenção de que esses registros têm `tipo_cadastro=veterinario`. Sem validação de tipo garantida a nível de banco.
- Duas FKs fantasmas confirmadas: [[vet_conhecimento_documentos]]`.revisado_por_id` e [[vet_evolucoes_internacao]]`.user_id` (ambas deveriam apontar para `users.id`).
- Nenhuma duplicação de tabela/tablename encontrada neste bloco — diferente dos blocos 1, 2 e 5.

O campo `perfil_comportamental_snapshot` de [[banho_tosa_agendamentos]], que à primeira vista sugeriria esse vínculo, é preenchido só com `pet.porte`/`pet.peso`/`pet.cor_pelagem` — atributos físicos do Pet, não dados comportamentais (agressividade, ansiedade etc.). *Docstring de `PerfilComportamental` (`veterinario_models.py`) corrigida para deixar explícito que o vínculo não existe hoje.*

## Bloco 8 — E-commerce & Pedido Integrado & Marketplaces

- **Padrão correto confirmado (mais um exemplo de boa referência)**: [[pedidos]] (checkout web/app) converte para [[Venda]] via `_integrar_venda_ao_motor()` → `VendaService.criar_venda(...)`, e só depois disparam `VendaPagamento`, DRE, `ContasReceberService.criar_de_venda` e contas a pagar de taxa de gateway. Não há FK de schema entre `Pedido` e `Venda` — o vínculo é só texto livre (`Venda.observacoes`) e uma `IdempotencyKey` (`ecommerce-venda:{pedido_id}`), mas o fluxo de negócio está correto.
- **Ambiguidade de nomenclatura importante**: [[pedidos]] (checkout nativo da loja) e [[pedidos_integrados]] (pedido importado do Bling/marketplace) são dois agregados **totalmente independentes**, sem FK entre si, resolvendo problemas de domínio diferentes — um vira Venda/financeiro, o outro nunca vira Venda e serve só para reserva/baixa de estoque e reconciliação fiscal com o Bling. Nomes parecidos sugerem parentesco que não existe estruturalmente; vale documentar isso claramente para quem for novo no time.
- **Mais uma ocorrência do padrão "ORM só para leitura, escrita via SQL cru"**: [[cliente_segmentos]] é lida via ORM em dashboards mas escrita 100% via SQL cru em `segmentacao_service.py` — risco de dessincronia entre schema Python e schema real do banco (mesmo padrão já visto em `comissoes_configuracao`/`comissoes_vendas` no bloco 3).
- **[[oferta_publicacao_tokens]]**: design deliberado de índice público cross-tenant (PK é o próprio token opaco) — vale confirmar a entropia/geração do token numa eventual auditoria de segurança, já que qualquer fraqueza ali tem impacto direto (acesso público por design).
- Várias FKs fantasmas pontuais (`Pedido.cliente_id`, `PedidoItem.produto_id`, `EcommerceAnalyticsEvent.product_id`/`pedido_id`, `EcommerceNotifyRequest.product_id`) — mesmo padrão recorrente em todos os blocos.
- Nenhuma duplicação de tabela e nenhum router morto encontrados neste bloco.

## Bloco 9 — Integrações externas (Bling, iFood, Stone, WhatsApp)

🔴 **Módulo Stone inteiro é código morto**: [[stone_transactions]]/[[stone_transaction_logs]]/[[stone_configs]] têm modelo bem formado (inclusive FKs corretas para `vendas`/`contas_receber`), mas nenhum arquivo do projeto fora de `stone_models.py` os importa — sem router, sem service, sem registro em `main.py`. Adicionalmente, [[stone_configs]] tem um comentário dizendo que a senha de conciliação é "criptografada AES-256-CBC", mas **nenhum código no arquivo de fato criptografa** — se o módulo for reativado sem corrigir isso, `client_secret` e afins ficam em texto puro no banco. Contraste com [[bling_connections]] e [[tenant_whatsapp_config]], que implementam criptografia real via `app.security.tenant_config_crypto`.
- **iFood segue o padrão "bypass" (como o veterinário)**: [[ifood_orders]] é um espelho isolado do payload do iFood, sem FK para `pedidos`/`vendas`/`clientes`/`produtos` — nada no código cria Venda, baixa estoque ou gera financeiro a partir de um pedido iFood. Diferente do padrão correto usado por [[pedidos]] (e-commerce nativo) e [[banho_tosa_atendimentos]].
- **Mais um caso de vínculo cross-tenant deliberado**: [[bling_company_tenant_links]] resolve o tenant a partir do `companyId` de um webhook do Bling antes de qualquer contexto de tenant existir — mesma categoria de exceção à isolação multi-tenant já vista em [[vet_partner_link]]. Tem checagem de conflito (um `company_id` não pode ser reivindicado por dois tenants), o que é um bom sinal de cuidado na implementação.
- **Duplicação estrutural (não é código morto de verdade)**: `bling_flow_monitor_routes.py` define seu próprio `APIRouter`, que nunca é registrado — mas `bling_routes.py` importa as funções handler individualmente e as reexpõe sob seu próprio router registrado. Funciona, mas é um padrão incomum que pode confundir quem for mexer nessas rotas.
- **Inconsistência de padrão de `tenant_id` dentro do próprio módulo WhatsApp**: `whatsapp/models.py`/`models_handoff.py` declaram `tenant_id` com `ForeignKey("tenants.id")` real; `whatsapp/security.py` (tabelas de LGPD/auditoria) usa o mixin genérico sem FK real. Mesmo módulo, dois padrões diferentes.
- **Bom exemplo de migração de segredo**: [[tenant_whatsapp_config]] mantém par de colunas legado/criptografado por segredo, com o setter migrando automaticamente e zerando o campo legado — vale usar como referência para outros módulos (aliás, seria o padrão certo para corrigir [[stone_configs]] se aquele módulo for retomado).

## Bloco 10 — RH (cargo, funcionário, contagem)
